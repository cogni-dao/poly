# Dashboard–Agent Parity Inventory

## Scope and status

This is **phase 1 of `task.1791070963`**: the field-level parity inventory **only**. The
proof phase — contract/security suites, real-Postgres RLS and `EXPLAIN` tests, and the
exact-SHA candidate/production scorecards — is a deliberate second PR, because it depends on
capabilities that **do not exist yet** (there is no generic `authorize()` seam, no
`account:read` scope, and no portfolio-snapshot capability to test against).

Governed by [capability-plane.md](capability-plane.md). Every invariant name used below
(`NO_PRIVILEGED_TRANSPORT`, `NO_FABRICATED_VALUES`, `RLS_BACKSTOP`, …) is defined there.

Everything in this document was verified by static reading at branch point
`origin/main` = `df8f1e6d` on 2026-10-06. No local test/build execution
(`NO_LOCAL_EXECUTION`).

### Why this file lives in `docs/spec/`

The brief suggested `docs/porting/`. It is placed here instead, deliberately:

- `docs/porting/` is reserved for **legacy-port** parity — `poly-parity-contract.md` and the
  **machine-generated** `poly-port-inventory.{json,md}`. A hand-authored file named
  `…-parity-inventory.md` sitting beside a generated `poly-port-inventory.md` would be read
  as tooling output and edited or regenerated by mistake. The two "parities" are unrelated:
  one is legacy-source byte parity, this one is UI↔agent read parity.
- This document is the artifact [capability-plane.md](capability-plane.md) Acceptance Check 3
  names: *"Every rendered dashboard data primitive maps to exactly one capability in the
  inventory."* It carries `implements: capability-plane-spec` so the two cannot drift.

## How to read the table

**Classification**

- **CSF** — *canonical saved fact*. Must reach parity: the same value for a session user, an
  external API key, and the poly-brain tool at one frozen cutoff.
- **AOA** — *actor-only affordance / mutation handle*. Explicitly **not** data parity. Either
  a UI capability gate or an id that exists to address a mutation. An agent holding
  `account:read` must never receive write authority from these, and their absence from an
  agent response is **not** a parity failure.
- **JX** — *justified exclusion*, with the reason in the row.

**Security-critical marker**

🔒 marks a row whose read is sourced from a `poly_trader_*` table. Per
[Carve-out 1](capability-plane.md#carve-out-1--rls_backstop-is-not-universal) those tables have
**no RLS at all** — not in either schema package and not in any migration (verified below) —
so **the capability is the only tenant clamp**. A missing or wrong filter on one of these rows
is a cross-tenant leak with no second line of defence.

**"Agent read today?"** means: can a *delegated external principal* obtain this fact today?
Read [the delegation trap](#the-delegation-trap-why-bearer-reachable--agent-reachable) first —
the answer is almost never a simple yes/no.

## The delegation trap: why "bearer-reachable" ≠ "agent-reachable"

This is the single most important correction in this document, and it changes the shape of
the parity gap. **It is not that the dashboard routes reject agents. It is that they answer
the wrong question without saying so.**

Three verified facts compose into the trap:

1. `app/src/app/_lib/auth/session.ts:20` is a **bare re-export**:
   `export { resolveRequestIdentity as getSessionUser }`. So every route importing
   `getSessionUser` from `@/app/_lib/auth/session` already accepts an agent bearer token.
   `/wallet/dashboard`, `/wallet/overview`, `/wallet/status`, `/wallet/execution`,
   `/copy-trade/orders`, `/copy-trade/targets`, and `/wallet/grants` **all** do.
2. `issueAgentApiKey` sets `sub` to a **`userId`**
   (`app/src/app/_lib/auth/request-identity.ts:91-93`), and `resolveRequestIdentity` returns
   `{ id: payload.sub }` (`:125-130`). An agent principal is therefore just another user id.
3. Those routes resolve the tenant as
   `resolveBillingAccountId(container.serviceAccountService, sessionUser.id)` — e.g.
   `wallet/dashboard/route.ts:53-56` — i.e. **from the caller's own id**, with **no grant
   check anywhere**, and `resolveBillingAccountId` **lazily creates** an account on miss
   (`billing-account-cache.ts:74-79`).

**Consequence.** A delegated agent calling `/wallet/dashboard` with a valid key is not denied.
It silently receives **its own freshly-created, empty tenant** — never the owner's account.
There is no scope, no grant, and no way to name the account to read. This is the mechanism
behind the production incident that opened `story.5004`: the delegation path is not merely
missing, it is **misleadingly present**.

Mitigating the worst case: `/wallet/dashboard` degrades through `emptyDashboard(...)`
(`tenant-wallet-dashboard-service.ts:719-767`), which returns **typed nulls** plus a
`no_trading_wallet` warning — `pol_gas: null`, `usdc_available: null`, `usdc_total: null`
(`:732-740`) — not zeros. That is `NO_FABRICATED_VALUES`-compliant. The frozen
`/wallet/balance` tombstone is the opposite: it returns **literal zeros** (`balance/route.ts:43-47`).

**The only three true delegated reads in the node** take `billing_account_id` from the wire and
gate it with `resolvePerformanceRead`:

| Route | billing_account_id from wire | Grant check | Advertised in `agent.json` |
| --- | --- | --- | --- |
| `research/copy-trade-pnl/route.ts` | `poly.research-copy-trade-pnl.v1.contract.ts:44` | `:84-87` | yes (`agent.json/route.ts:142-153`) |
| `research/copy-trade-investigation/route.ts` | `:38-39` | `:69-72` | **no** |
| `research/copy-trade-investigation/evidence/route.ts` | `:38-39` | `:78-81` | **no** |

`resolvePerformanceRead` (`app/src/features/agent-grants/authorization.ts:34-37`) is
owner-first (`:38-51`), then falls back to an active, non-revoked, unexpired grant
(`:53-65`), with the scope as a **literal in the function body** at **`:62`**
(`arrayContains(agentCapabilityGrants.scopes, ["performance:read"])`).

> **ALIAS-CASE ANCHOR (amendment 1).** `:62` is the exact line the `performance:read` →
> `account:read` rename must make scope-set-matching rather than literal, in **both** this
> function and the delegated RLS policies. A grant row holding **only** `performance:read`
> must keep authorizing `account:read` reads, or the one live production grant breaks with no
> human re-approval. This is the single highest-value regression row in the matrix.

Discovery is narrower still: `requiredScope` appears **exactly once** in the whole discovery
route — `requiredScope: "performance:read"` at
`app/src/app/.well-known/agent.json/route.ts:147`. `readCopyTradePnl` is the **only** poly
account-data read an agent can discover. The investigation and evidence routes are reachable
but undiscoverable.

Two traps for the parity test, both verified in code:

- **`pnlUsd` is overwritten by a display overlay.** `applyRealizedPnl`
  (`tenant-wallet-dashboard-service.ts:272-274`) rewrites `pnlUsd` to *lifetime realized* P/L.
  Market exposure (§7) is deliberately fed the **pre-overlay** arrays
  (`marketLivePositions` / `marketClosedPositions`, `:264-265`) because its cost-basis math
  depends on the original `currentValue − pnlUsd` relation (`:260-263`). A parity test must
  compare post-overlay values for §6 and pre-overlay values for §7, or it will report a false
  mismatch.
- **`currentValue` is zeroed only for terminal lifecycle states** —
  `WALLET_EXECUTION_TERMINAL_LIFECYCLE_STATES` (contract `:68-74`) deliberately **excludes**
  `abandoned`, because abandoned shares are still on chain (contract `:53-66`, bug.5040).
